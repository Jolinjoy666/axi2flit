### 2.2 SystemC 行为模型与新增 RTL 的区别

有时钟和逐拍握手说明模型表达了接口时序，但不足以证明内部实现与寄存器传输级对应。原有 SystemC 实现使用动态容器、消息对象及一拍内多次函数处理；例如 Target 在一个时钟沿调用 `receive → collect → assemble → submit → transmit`，部分逻辑在同一仿真时间内完成。

RTL 级模型需要明确寄存器、固定容量存储、状态转移、组合逻辑/流水边界，并证明相应逐周期行为。SystemC 语言本身可以用于不同抽象层次，不能仅凭语言或 `SC_THREAD` 名称判定为 RTL。当前[设计文档](../systemc/doc/design.md)也明确将实现界定为行为模型，不能用仿真设定的 500MHz 推导综合主频。

新增 `rtl/` 已采用固定深度存储、寄存器与组合逻辑，现有行为编解码用于逐消息字节参考，时钟断言检查背压保持。两者不是逐周期等价实现，尤其仲裁、流水和吞吐不同。28nm 工艺后仿等仍属于后续设计数据及报告交付，不能以 Verilator 通过代替工艺综合结果。

### 2.3 两类 Target 与实际 Flit2DFI 的差距

`AouTarget` 已做到：读取 RREQ/WREQ/WDATA，按 RP 内写请求顺序组装 W 数据，用 `AWLEN+1` 恢复突发边界；读请求或完整写突发通过 `mem_req` 提交，后端结果通过 `mem_rsp` 返回并恢复 RLAST/B 响应。

`SimpleMemRequest` 仍包含整笔地址属性和全部写数据。它没有建立实际 MC 命令粒度、命令编号与返回关联，也没有与 DFI 命令/数据事件进行映射验证。因此现阶段可以称为“Flit 到存储事务适配”，不能直接宣布已完成合同中的 Flit2DFI。

新增 RTL 已把 burst 拆为逐拍、带 tag 的 MC 命令，支持 SIZE/lane/WSTRB、命令背压、乱序完成收集和响应聚合；TB 已独立比较每条命令，但尚未连接实际 MC。它选择下表第一类 MC 请求侧边界。后续与成果 4 的 MC 开发者协作时，应确认此边界与实际对端能力一致：

| MC 提供的接口 | 成果 2 应完成的适配 | MC 侧职责 |
|---|---|---|
| MC 接收整突发或读写请求 API，由 MC 输出 DFI | 将 `SimpleMemRequest` 转为 MC 接受的请求，处理拆分、掩码、背压、响应聚合和 ID；验证请求最终产生正确命令和读写结果 | bank/通道调度、DRAM 命令生成、DFI 输出及时序 |
| 协作约定要求适配器直接交付 DFI 级命令/数据事件 | 在现有事务还原之后增加约定的命令/数据映射、相位和完成关联，并接上对端检查 | 明确哪一侧负责调度、时序约束及 PHY 交互，避免职责重复或遗漏 |

无需在成果 2 内重复实现整套 MC/MEM PHY，但必须给出“输入 Flit 最终对应哪些 MC 命令”的可追踪证据。`reference/mem_sim` 中已有独立 MC/DFI 相关内容，可作为候选协作对象；当前全链路测试没有实例化它，不能直接计为适配完成。

“原子化读写命令”在这里应解释为双方约定的最小存储操作粒度，不自动等于 AXI atomic 或独占访问。例如约定 MC 每条请求覆盖 64B，则 16 拍×128B 的全宽写可能拆成 32 条请求；这是接口方案示例，不是当前代码已实现的行为。

## 3. 格式和数据映射如何计算、如何判断正确

### 3.1 AXI 突发与存储字节的对应

对当前支持的 INCR 突发，设首地址为 `A`、总线字节数为 `W`：

```text
N          = AxLEN + 1                         突发拍数
s          = 2^AxSIZE                          每拍访问字节数
Addr(k)    = A + k×s                           第 k 拍字节地址
Lane(k)    = Addr(k) mod W                     该拍有效数据起始 lane
请求字节数 = N×s                              不是固定 N×W
有效写字节 = Σ 各拍合法访问 lane 中 WSTRB 非零的字节数
```

第 k 拍第 j 个有效字节对应 `memory[Addr(k)+j]` 和 `data[Lane(k)+j]`；写入还必须满足对应 WSTRB 有效。读响应根据同一地址映射还原到 AXI 数据 lane。1024 位总线上的 4B 窄访问每拍只有 4B 应用数据。

若下游按对齐的 `q` 字节块接受命令，则连续区间 `[A,A+D)` 覆盖的块数为：

```text
N_blocks = ceil(((A mod q)+D)/q)
```

这只给出待覆盖块数，不规定实际 DRAM 命令条数。还需要按下游能力处理 bank/行边界、块内掩码、请求拒绝和响应聚合；缺少这些约定时，不能把“一笔 AXI burst”等同于“一条 DFI 命令”。

### 3.2 消息与 Flit 的对应

| AXI 通道 | AoU 消息 | 当前后端含义 |
|---|---|---|
| AW | WREQ | 建立写请求地址、长度、属性上下文 |
| W | WDATA 或 WDATAFULL | 按 AW 顺序补齐写突发；全选通时省去显式 WSTRB |
| AR | RREQ | 建立读请求 |
| R | RDATA | 逐拍还原读数据、ID、响应与 LAST |
| B | WRESP | 返回写完成状态与 ID |

```text
1 granule = 5B
256B 物理帧 = 2B FH + 4B CRC + 10B AoU PH + 240B 消息区
250B FDI 内容 = 10B AoU PH + 240B 消息区
240B 消息区 = 48 granule
```

1024 位下，RDATA 和 WDATAFULL 每条为 27 granule=135B，带选通 WDATA 为 30 granule=150B；WREQ/RREQ 各 3 granule=15B，WRESP 为 1 granule=5B。消息可以跨帧，不能只检查每帧是否能独立解出整条消息。接收端用 MsgStart 和消息头确定边界，不依赖发送端辅助统计字段。

### 3.3 正确性判据

在有效请求全部完成、各级队列排空后，基本守恒关系为：

```text
N_AW = N_WREQ = N_后端写事务 = N_B
N_AR = N_RREQ = N_后端读事务
N_W  = Σ 已接受 AW 的 (AWLEN+1)
N_R  = Σ 已完成 AR 的 (ARLEN+1)
```

上述是 SystemC“一笔 burst 对应一笔后端事务”的关系。新增 RTL 中 `N_MC_write=N_W`、`N_MC_read=N_R`，每个 beat 对应一条命令，每条命令须返回一次完成；父事务的 B 仍恰好一次，所有读数据按原 burst 顺序返回。

同时必须检查：地址与数据逐字节一致、WSTRB、ID/USER/RESP、WLAST/RLAST、同 ID 顺序、背压时信号稳定、credit 不超发，以及没有丢失/重复响应。仅检查事务数量或仿真无崩溃不足以证明正确。

当前全链路记分板只依据 AXI 握手维护独立字节参考存储，不读取被测内存作为期望值。支持范围仍有边界：简单内存不执行独占监视器；运行期间单端热复位不支持；已有固定种子测试不等于所有并发组合均覆盖。

## 4. 协议转换延迟怎么算，是否满足 20ns

### 4.1 SoC 侧 SystemC 历史测量公式与结果

来源：[tb_axi2flit_perf.cpp](../systemc/tb/tb_axi2flit_perf.cpp) 的 PERF-3。它使用实际握手时间戳，部分打印标签中的 `ARVALID/RVALID` 不应理解为首次拉高 VALID 的时刻。

```text
L_TX_read  = t(对应请求消息完整离开桥) - t(AR 握手)
L_TX_write = t(最后写数据消息完整离开桥) - t(WLAST 握手)
L_RX_read  = t(R 握手) - t(对应响应 Flit 入站握手)
L_RX_write = t(B 握手) - t(对应响应 Flit 入站握手)

L_avg      = Σ L_i / 样本数
L_max      = max(L_i)
同笔桥合计 = L_TX_i + L_RX_i
样本保守上界 = max(L_TX_i) + max(L_RX_i)
```

当前结果来自 RP1、2ns 时钟、初始化完成后的空载单拍，RREADY/BREADY 恒高，每种位宽分别采集 20 个读和 20 个写样本：

| 位宽 | 读 TX 平均/最大 ns | 写 TX 平均/最大 ns | R/B RX 平均/最大 ns | TX+RX 样本保守上界 |
|---:|---:|---:|---:|---:|
| 256 | 4 / 4 | 4 / 4 | 4 / 4 | 8ns |
| 512 | 4 / 4 | 4 / 4 | 4 / 4 | 8ns |
| 1024 | 7.80 / 8 | 4.20 / 8 | 4 / 4 | 12ns |

因此，**SoC 侧桥在这些测试条件下满足 20ns**。20ns 相当于当前时钟的 10 拍，样本合计上界为 6 拍。

但自动门限只检查 `TX平均≤12ns`、`RX平均≤8ns`，没有自动对每笔事务检查 `TX+RX≤20ns`；表中的上界是有限样本最大值相加。PERF-3 也没有实例化 `UcieAouAdapter` 和 `AouTarget`，不能代表整个成果 2 的所有转换边界。

### 4.2 存储侧 Flit→MC/DFI 应补测的公式

应为每笔父事务和下游子命令建立关联，区分数据到齐、解码组装、排队与命令接受：

```text
t_req_ready = 构成该事务所需的请求及数据最后片段在约定入口可用的时刻
              读通常是 RREQ 完整到达；写需要对应 WREQ 和必需 WDATA
L_target    = t(后端事务被接受) - t_req_ready
L_cmd_first = t(第一条对应 MC/DFI 命令被接受) - t_req_ready
L_cmd_last  = t(最后一条对应 MC/DFI 命令被接受) - t_req_ready
L_return    = t(对应响应最后片段离开适配器) - t(后端响应可用)
```

若适配器允许数据边到边发，还应记录每个分片自己的可用与接受时间；不要用“整笔数据最后到达”去计算已经提前发出的首条命令延迟。建议同时记录 FDI 入队、Target 取出、完整事务生成、MC 接受和 DFI 事件时间，避免把 Target 入口队列等待漏掉。

当前 `receive/assemble/submit` 中多个处理步骤可以发生在同一仿真时间，测到 0 个额外周期只代表行为模型的调度方式，不能推导实际 RTL 的组合逻辑零延迟。

正式应用 20ns 门限前，需要在模块接口约定中明确：测哪一侧、是否包含 Adapter、按首条还是末条命令、是否包含外部背压。无外部等待时测固有转换延迟；有背压时另报排队和停顿。若允许下游无限期不接收，则无法保证包含全部等待的 20ns 上界。

### 4.3 端到端访存延迟不等于转换延迟

完整访问还包括链路与存储服务：

```text
L_read = SoC请求转换 + 正向链路/排队 + Target转换
       + 存储服务/排队 + 响应转换 + 反向链路/排队 + SoC响应交付
```

本次 [256 位 RP1 CSV](../systemc/sim/full_link_256_rp1.csv) 中，单拍读 AR=230ns、R=278ns，得到 48ns；单拍写 AW=290ns、WLAST=294ns、B=342ns，得到 AW→B=52ns、WLAST→B=48ns。其中包含简单内存单拍 `20+2=22ns` 等时间，不能直接拿 48ns 判定桥新增延迟超过 20ns。

## 5. 转换吞吐与格式效率：作为本模块能力证据

本节下表为原有 SystemC 桥基线；RTL 实测已单列在 [RTL 验证说明第 5 节](RTL协议桥验证说明.md#5-持续吞吐1024-位已接近当前协议与链路预算上限)，两者不能替代。

90% 是项目全链路指标，不能仅凭成果 2 的桥基线宣布全项目达标。这里保留与转换模块相关的公式，作为后续联合验收输入。

默认速率配置为 x16、每 lane 24G 符号/s、NRZ，每符号 1bit。本地模型的符号率与调制参数分别设置，不能对其他模型已经表示等效比特速率的 GT/s 再重复乘 2。

```text
B_raw     = lane数 × 符号率 × 每符号bit数 / 8
          = 16×24×1/8 = 48GB/s（单向）
T_flit    = 256/48 = 5.33333ns
B_payload = B_raw×240/256 = 45GB/s
B_AXI     = (AXI位宽/8) / 时钟周期ns = 16/32/64GB/s
```

沿用项目约定剔除 16B 固定帧开销，240B 消息区内的消息头、掩码、填充和 credit 等仍计入成本。GB/s 为十进制单位，数值与 B/ns 相同。

```text
D      = 测量窗口内有效应用数据字节
Δt     = 测量窗口时间
F      = 同一窗口、数据方向实际传输的帧数
B_app  = D/Δt                                      应用吞吐
η_B    = D/(F×240)                                 已发送帧的载荷效率
ρ      = F×T_flit/Δt                               链路时间占用率
η_time = B_app/B_payload = η_B×ρ                    计入空闲的利用率
```

因此“帧内效率 95%”但仅有一半时间发送时，实际时间利用率为 47.5%。`η_B` 不能独立证明持续带宽。读按 RX、写按 TX 分别统计；混合读写若报告合计，分母也须使用双向容量。

本次重新运行桥性能基线：预热 600 拍、测量 2000 拍=4000ns，RP1、16 拍全宽突发、最多 64 笔在途。

| 位宽 | 读吞吐 GB/s | 写吞吐 GB/s | 1024 位数据方向帧内效率 |
|---:|---:|---:|---|
| 256 | 16.00 | 16.00 | 不适用；受 AXI 能力限制 |
| 512 | 32.00 | 32.00 | 不适用；受 AXI 能力限制 |
| 1024 | 42.656，显示 42.66 | 42.40 | 读 94.79%、写 94.22% |

1024 位纯读窗口内为 1333 拍、750 帧：

```text
D=1333×128=170624B
B_app=170624/4000=42.656GB/s
η_B=170624/(750×240)=94.7911%
ρ=750×(256/48)/4000=100%
η_time=42.656/45=94.7911%
```

纯写为 1325 拍，即 `169600/4000=42.40GB/s`，`η_B=169600/(750×240)=94.2222%`。当前写吞吐按 W 握手计接受数据，不能当作后端已完成写入的带宽。窄访问按 SIZE、掩码写按有效 WSTRB 计算应用字节；完整链路写完成吞吐还应按成功 B 响应关联事务计数。

1024 位读转换的理想协议容量为 `45×128/135=42.6667GB/s`。16 拍全选通写计入 WREQ 后为 `45×2048/(15+16×135)=42.3724GB/s`。有限窗口请求头与数据可能落在不同边界，因此实测 42.40 略高于长期估算不代表超越物理限制。

上述测试使用简化链路和模式响应器，证明桥基线有较高吞吐；完整 `UcieLink+Target+Memory` 的持续能力还会受到窗口和后端服务限制。已有[延迟、带宽与 credit 分析](端到端延迟、带宽与credit容量分析.md)记录了这类限制，本文不将其扩展为成果 2 必须独立完成的存储器性能整改任务。
